# Emergent Codes

*English version: [README.md](README.md)*

Симуляция передачи информации между узлами с искажениями, построенная ради одного вопроса: **может ли популяция спонтанно выработать помехоустойчивый код?**

---

## Проблема

При передаче информация меняется. Получатель не копирует сообщение — он восстанавливает его из того, что у него уже есть. И всё же сообщения остаются узнаваемыми через много пересылок.

Поэтому интересно не то, откуда берётся изменчивость, а то, откуда берётся **устойчивость** при постоянных искажениях.

Одно правдоподобное объяснение: искажения не случайны. Они направлены, причём примерно в одну сторону у разных получателей, поэтому сообщения не расходятся, а сходятся к формам, которые легко удерживать. В существующих моделях эти формы задаются вручную как параметр. Здесь они не задаются вообще.

## Связь с теорией кодирования

Устойчивая форма делает ровно то же, что кодовое слово: искажённое сообщение притягивается обратно к ближайшему допустимому, поэтому ошибки не накапливаются от пересылки к пересылке.

Разница в том, что код проектируют заранее, а здесь множество допустимых слов должно возникнуть само.

**Гипотеза.** Минимальное расстояние эмерджентного множества растёт с уровнем шума в канале — система подстраивает свою избыточность под условия передачи.

---

## Как это устроено

Узлы обмениваются двоичными векторами фиксированной длины `n` по зашумлённому каналу. Каждый узел хранит набор взвешенных записей. Нигде не указано, какие векторы «правильные».

**Приём.** Входящий вектор сопоставляется с ближайшей записью по расстоянию Хэмминга. Достаточно близко — запись подкрепляется и сдвигается к входу побитовым большинством. Слишком далеко — создаётся новая запись. Это декодирование по минимуму расстояния, только эталонное множество накапливается, а не задаётся.

**Отправка.** Запись выбирается с вероятностью, пропорциональной её весу, и передаётся; каждый бит инвертируется с вероятностью `p`.

**Роли.** Каждая передача несёт метку роли — просто целое число из `[0, R)` без внутренней структуры. Она обозначает, *о чём* сообщение, отдельно от того, *как* оно выглядит. Если получатель относит входящий вектор к записи другой роли, эта запись штрафуется.

Роли нужны потому, что без них система схлопывается: слияние стягивает всё к одному вектору, который идеально устойчив и совершенно бесполезен. Требование различать `R` вещей — вот что расталкивает векторы; то же требование даёт коду его минимальное расстояние.

**Забывание.** Веса затухают каждый тик; записи ниже порога удаляются. Ёмкость ограничена конкуренцией, а не заданным потолком.

## Что измеряется

После прогона записи всех узлов объединяются и кластеризуются по расстоянию Хэмминга. Центры кластеров — кандидаты в кодовые слова, их множество `C` — эмерджентный код.

| Величина | Смысл |
|---|---|
| `n` | длина вектора (фиксирована) |
| `\|C\|`, `k = log₂\|C\|` | сколько различных слов выжило |
| `d` | минимальное расстояние между различными словами |
| `d_roles` | минимальное расстояние между словами *разных* ролей (синонимы не учитываются) |
| `d_top` | минимальное расстояние кода из самого тяжёлого слова каждой роли (ровно `R` слов) — основная метрика |
| чистота | доля веса кластера, приходящаяся на его доминирующую роль |
| доля ошибок | измеряется напрямую: `C` пропускается через канал и декодируется |

Затем это сравнивается с границами Хэмминга (упаковки шаров) и Синглтона, а также с известными кодами с теми же параметрами.

## Эксперименты

| # | Что варьируется | Вопрос |
|---|---|---|
| 1 | `θ`, `λ` | где границы между коллапсом, устойчивостью и рассыпанием? |
| 2 | **`p`** | **растёт ли `d` с шумом канала?** (главный результат) |
| 3 | `R` при фиксированном `n` | в какой момент система перестаёт справляться и как это соотносится с границей Хэмминга? |
| 4 | `N`, `L` | устойчив ли результат к размеру популяции и её обновлению? |
| 5 | `p = 0` | возникает ли что-то новое без шума? (контроль) |
| 6 | старт с кода Хэмминга [7,4] | сохраняет ли динамика хороший код? (контроль) |

Каждая конфигурация запускается не менее 30 раз с разными сидами; результаты усредняются, приводится разброс.

---

## Ограничения дизайна

- **Двоичные векторы, расстояние Хэмминга.** Классические границы определены именно в этих терминах; иначе сравнение было бы невозможно.
- **Никакого допустимого множества в коде.** Если бы оно было задано, результат был бы заложен, а не получен.
- **Шум в канале.** Без него «помехоустойчивость» ничего не значит.
- **Случайная инициализация.** Чем беднее начальная точка, тем сильнее результат. Пустые хранилища и заранее заданные коды используются только как контроль.
- **Никаких нейросетей.** Каждый наблюдаемый эффект должен сводиться к причине, что исключает обучаемые чёрные ящики.

## Запуск

Python 3.11+, только NumPy.

```bash
python3.11 -m venv .venv && .venv/bin/pip install -e '.[dev]'

# одиночный прогон; любое поле SimConfig переопределяется как KEY=VALUE
.venv/bin/python -m emergent_codes run --set noise=0.05 n=12 n_roles=4 --snapshot-every 500

# варьировать один параметр по нескольким сидам (параллельно), строки прогонов — в CSV
.venv/bin/python -m emergent_codes sweep noise 0,0.02,0.05,0.1 --seeds 30 --out results/noise.csv

.venv/bin/pytest
```

Структура кода (`emergent_codes/`):

| Модуль | Содержимое |
|---|---|
| `config.py` | `SimConfig` — все параметры, в комментариях обозначения из README |
| `channel.py` | двоичный симметричный канал |
| `node.py` | хранилище записей: приём (декодирование по минимуму расстояния), выбор, забывание |
| `simulation.py` | динамика популяции, режимы инициализации (`random`, `empty`, `hamming74`), обновление популяции |
| `analysis.py` | объединение и кластеризация записей в `C`; `\|C\|`, `k`, `d`, чистота, ошибка декодирования, границы |
| `codes.py` | расстояние Хэмминга, границы Хэмминга и Синглтона, код Хэмминга [7,4] |
| `cli.py` | команды `run` и `sweep` |

Решения v0.1, которые текст выше оставляет открытыми:

- говорящий выбирает роль равновероятно, затем запись этой роли по весу; если записи для роли нет, он придумывает случайный вектор и сохраняет его;
- при совпадении с записью другой роли её вес умножается на `role_penalty`, **и** вход сохраняется как новая запись правильной роли;
- новые узлы при обновлении популяции стартуют пустыми;
- кластеры с долей менее 2% общего веса считаются шумом, а не кодовыми словами.

Скрипты экспериментов (`experiments/`, сырые результаты — в `results/`, который не попадает в git):

| Скрипт | Серии |
|---|---|
| `v01.sh` | развёртка по шуму, карта `θ × λ`, число ролей, контроль [7,4], развёртка по шуму при больших `θ` |
| `v02.py` | общность по `n` и `R`, длинные прогоны при `R = 1`, контроль [7,4] при `R = 16`, анализ потолка `d` |
| `v02_checks.py` | контроль [7,4] с `λ`, масштабированным по `R`; общность с `θ`, масштабированным по `n` |
| `v03.py` | число ролей при `λ ∝ 1/R`; `n = 16…24` на 30 сидах |

## Промежуточные выводы (v0.1–v0.3)

Если не оговорено иное: `N = 20` узлов, 10 000 тиков, `role_penalty = 0.1`, `λ = 0.12 / R` (0.03 при `R = 4`).
Числа — среднее ± стандартное отклонение по сидам; «значимо» означает, что наклон `d_top` по `p` имеет `|t| ≥ 3`.
Это разведочные серии: по 10 сидов, если не указано 30, — меньше стандарта в 30 сидов для итоговых результатов.

**1. В режиме плотной упаковки шум увеличивает минимальное расстояние.** При `n = 12, R = 4, θ = 2` (30 сидов)
`d_top` растёт с 4.0 ± 0.85 при `p = 0` — не лучше случайного кода из 4 слов (3.8) — до 5.5 ± 0.7 при `p = 0.04`;
все роли на месте, чистота ≈ 1. Наклон значим при `n = 8` (`R = 2, 4`), `n = 12` (`R = 2, 4`) и `n = 16`
(`R = 4`: t = 4.7, `R = 8`: t = 4.5, по 30 сидов); слабее при `n = 12, R = 8` (t = 2.2) и отсутствует при
`n = 8, R = 8`, где система перегружена (чистота 0.64).

**2. Это не общий закон.** Эффект исчезает, когда случайные слова уже далеко друг от друга относительно `θ`:
при `n = 20` он на грани значимости (t ≈ 2), при `n = 24` его нет (30 сидов), при `R = 2` и `n ≥ 16` — никогда.
Уточнённая гипотеза: *`d` растёт с `p`, пока код плотно упакован (`d` случайного кода в пределах примерно
`θ + 2…4`), а шум остаётся ниже радиуса декодирования.*

**3. Слишком сильный шум разрушает код, а не улучшает его.** Слом определяется ожидаемым числом искажённых бит
`n·p` относительно `θ`, а не самим `p`: при `n = 12, θ = 2` он наступает при `p ≈ 0.05–0.06` (код распадается на
10–13 слов со смешанными ролями, чистота 0.5–0.75); при `θ = 3` сдвигается к `p ≈ 0.07`; при `n = 20–24` и `R ≥ 4`
роли теряются уже при `p = 0.04`. Поэтому окно полезного шума сужается с ростом `n`.

**4. `d` останавливается намного ниже оптимума.** При `n = 12, R = 4` `d_top` выходит на 5.6–5.8 примерно к 10 тыс.
тиков и не меняется до 50 тыс. ни при каком `θ ∈ {2, 3, 4}`; оптимум — 8 (Плоткин, `A(12, 8) = 4`). Код похож на
*случайный код с запретной зоной*: у случайных кодов из 4 слов при условии `d ≥ 5` / `d ≥ 6` среднее 5.15 / 6.01.
Две причины:
- отталкивание короткодействующее: вероятность, что зашумлённая копия попадёт в пределы `θ` от слова другой роли,
  падает в 15–20 раз на единицу расстояния (при `θ = 2, d = 6, p = 0.04` — 3·10⁻⁵ на сообщение);
- слова почти неподвижны: при `θ = 4` сила при `d = 6` ещё 1.7·10⁻², но `d` тоже не растёт, потому что вектор
  большинства тяжёлой записи почти не сдвигается, а новые варианты появляются только как шумовые копии рядом с ним.

**5. Ёмкость по ролям падает с шумом и намного ниже границ.** При `n = 12, θ = 2` и `λ ∝ 1/R` все 16 ролей
выживают при `p = 0.02` (чистота 0.99; около 20 из 32 при `R = 32`), но лишь ~6 при `p = 0.05`. В плотном режиме
`d_top` прижат к `θ + 1 = 3`. Для сравнения: граница Хэмминга при `n = 12, d = 3` — 315 слов.

**6. Забывание должно масштабироваться с числом ролей.** Каждая запись подкрепляется примерно раз в `R` сообщений,
поэтому при фиксированном `λ` большие `R` теряются из-за забывания, а не из-за шума: узел, забывший роль, придумывает
для неё случайный вектор. При `λ = 0.03` заданный код [7,4] при `R = 16` разваливался даже при `p = 0`, а кажущийся
предел ~8 ролей в v0.1 был этим артефактом. Существенные безразмерные величины — `λ·R` и `n·p / θ`.

**7. Контроли.**
- *Хэмминг [7,4], `R = 16`, `θ = 1`, `λ = 0.003`:* заданный код сохраняется целиком (16/16 слов на своих ролях,
  `d = 3`) при `p ≤ 0.02` и почти целиком при `p = 0.05` (15.4/16). Случайный старт при тех же параметрах ни разу не
  доходит до `d = 3` (`d_top` 1.6–2.0). Динамика сохраняет хороший код, но плотный сама не находит.
- *Без ролей (`R = 1`):* при наличии шума популяция *не* схлопывается в один вектор. За 60 тыс. тиков при `p = 0`
  она медленно укрупняется (4.6 → 1.6 слова, доля главного слова 0.41 → 0.85), но при `p = 0.05` разнообразие
  стационарно (≈5 слов, доля главного ≈0.45, 15% сообщений создают записи): баланс мутаций и дрейфа. Получаются
  синонимы без расхождения (`d ≈ 3`), а не код. Шаг 2 роадмапа верен только в пределе без шума.

**Открытые вопросы.** Что ограничивает ёмкость ~20 ролями при `p = 0.02`, если геометрия допускает гораздо больше?
Сломает ли потолок запретной зоны механизм, позволяющий словам двигаться (а не только отбираться), и укладывается ли
такой механизм в ограничения дизайна выше?

## Статус

v0.3: модель, измерения и инструменты развёрток реализованы и покрыты тестами; разведочные серии выше проведены.
Значения по умолчанию (`decay = 0.03`, `role_penalty = 0.1`) подобраны для `R = 4`; для других `R` используйте
`decay = 0.12 / R`.

Роадмап:

1. Один узел, замкнутый на себя
2. Популяция без ролей — подтвердить, что она вырождается
3. Роли включены; найти область параметров, где репертуар выживает
4. Развёртка по шуму — главный результат
5. Контроли
6. Сравнение с границами и известными кодами
